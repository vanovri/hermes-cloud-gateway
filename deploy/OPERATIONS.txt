Wait until the new verification run appears. Check its revision matches the push.
Then watch it and queue the gateway only if verification succeeds:

$verification = gh run list --repo vanovri/hermes-cloud-gateway --workflow verify.yml --limit 1 --json databaseId | ConvertFrom-Json
gh run watch $verification[0].databaseId --repo vanovri/hermes-cloud-gateway --exit-status
if ($LASTEXITCODE -ne 0) { throw 'Verification failed. Gateway dispatch stopped.' }
gh workflow run hermes.yml --repo vanovri/hermes-cloud-gateway --ref main

Concurrency preserves the active gateway. The replacement waits for the current
cycle to finish and publish state. Do not cancel the active run to accelerate this
handoff. Later dispatches may replace queued runs. Confirm the deployed revision
and fresh timestamp in the readiness receipt after the replacement starts.

A green receipt is a timestamped observation, not a continuous guarantee. Health
checks do not invoke a model or send a message. Inference and delivery require a
separately authorized functional smoke test with actual acknowledgments.

Prepare a dedicated Ubuntu or Debian server

Run as the non-root service account. Install GitHub CLI and authenticate first.
The supplied unit expects exactly ~/hermes-cloud-gateway.

gh auth login
gh repo clone vanovri/hermes-cloud-gateway "$HOME/hermes-cloud-gateway"
cd "$HOME/hermes-cloud-gateway"
bash deploy/prepare-runtime.sh
python3 -m unittest discover -s tests -v
python3 ops/verify_core.py --core "$HOME/.hermes/hermes-agent"

Provision memory for the OS in addition to the service's 4 GiB limit. The unit
uses MemoryHigh=3G, MemoryMax=4G, TasksMax=512, LimitNOFILE=65536. Node heap is
limited to 1,536 MiB. Persistent disk must hold state and retained logs.

Transfer gateway ownership before enabling systemd

Perform these steps only during server migration. They disable future cloud
dispatches and cancel queued cycles, while allowing the active cycle to save state.

gh workflow disable watchdog.yml --repo vanovri/hermes-cloud-gateway
gh workflow disable hermes.yml --repo vanovri/hermes-cloud-gateway
for run in $(gh run list --repo vanovri/hermes-cloud-gateway --workflow hermes.yml --status queued --limit 100 --json databaseId --jq '.[].databaseId'); do
  gh run cancel "$run" --repo vanovri/hermes-cloud-gateway
done
for run in $(gh run list --repo vanovri/hermes-cloud-gateway --workflow hermes.yml --status in_progress --limit 100 --json databaseId --jq '.[].databaseId'); do
  gh run watch "$run" --repo vanovri/hermes-cloud-gateway
done
gh run list --repo vanovri/hermes-cloud-gateway --workflow hermes.yml --limit 5

Require no active or queued cloud gateway. Confirm the last state publication
succeeded. Its final dispatch may fail because the workflow is disabled. If
publication failed, reconcile the retained encrypted artifact before migration.
Stop an old default gateway unit if present on the destination host:

systemctl --user disable --now hermes-gateway.service

systemd restarts both successful and failed exits after five seconds without a
start-rate limit. It kills a frozen supervisor after 60 seconds without a watchdog
notification. The supervisor allows up to 60 seconds for gateway drain while
keeping the router available, then terminates remaining descendants. The unit's
TimeoutStopSec=80 sets the final shutdown deadline. Readiness requires Telegram
and the built-in scheduler, matching this deployment profile.

Log retention on the dedicated host

Each captured process retains approximately 120 MiB. Standard Hermes logs retain
their existing smaller rotation limits. Request-body logging is disabled. Watchdog
diagnostics rotate internally. This optional journal configuration affects all
services on the dedicated host: 512 MiB persistent, 128 MiB runtime, 14-day age.

sudo mkdir -p /etc/systemd/journald.conf.d
sudo install -m 644 deploy/journald-retention.conf /etc/systemd/journald.conf.d/60-hermes-retention.conf
sudo systemctl restart systemd-journald
journalctl --disk-usage

deploy/hermes-logrotate.conf is an optional extra policy for third-party diagnostic
files. Replace @HOME@ with the service account's absolute home before installation.
Internal watchdog rotation does not depend on logrotate.

Recovery boundaries

The systemd service stores state on its persistent disk. It does not publish
GitHub state generations after migration. Back up that disk before relying on it
against disk loss. Do not re-enable cloud from an older state/live generation
after the server accepts new work. Reverse migration needs the latest server
state through the verified encrypted recovery protocol.

Actions remains best effort. Handoffs interrupt service. Schedules can be delayed
or dropped. Abrupt runner loss can lose changes since the last published state,
up to a 17,400-second active cycle plus startup and publication time. Credential
revocation needs valid replacement credentials. Single-host storage failure needs
backups or another host. Process restarts cannot remove those dependencies.

No production soak, real provider outage, or physical server reboot was performed.
Local fault drills and config validation establish only their tested behavior.
